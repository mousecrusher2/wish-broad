# アーキテクチャノート

このドキュメントでは、複数のモジュールにまたがる設計判断、ライフサイクル、トレードオフ、運用手順を記録します。特定のモジュールや関数の中だけで完結する設計意図や制約は該当箇所のコードコメントに書き、ここには記載しません。

本アプリケーションは、公開 WHEP との相互運用性ではなく、Discord の画面共有よりも高画質な認証付きライブ視聴に最適化しています。

## ランタイムモデル

Worker はステートレスなリクエスト処理の仲介役（接着層）として設計しています。リクエストをまたいで保持すべき永続状態は単一の Durable Object である `LiveState` に集約し、実際のメディアセッションとトラック状態は Cloudflare Realtime SFU（旧称 Cloudflare Calls、`CALLS_*` というシークレット名の由来）が管理します。アクティブな全セッションを定期的にポーリングしたり、長寿命のインメモリ状態を保持したりする設計は採りません。

`LiveState` は配信情報、配信者トークン、ユーザー情報を自身の SQLite ストレージに保持し、ルートからは `worker/live-state.ts` の `getLiveState(env)` が返す RPC メソッド経由でアクセスします。`/api/lives` がすべての配信とその配信者名をまとめて取得する必要があり、視聴者・配信者の各アクションにかかる負荷も数回の短い呼び出しで済むため、単一のオブジェクトに全状態を集約しています。`LiveState` クラス本体は `worker/live-state.ts` に実装しており、`worker/main.ts` はそれを `LiveEffects` や Hono アプリとともに再エクスポートするだけです。

Durable Object は実行中および応答待ちの実時間（wall-clock time）に対して課金されるため、`LiveState` は Realtime SFU・Discord・その他の外部 API を決して呼び出してはならず、自身のストレージおよびアラーム呼び出し以外のものを `await` してはなりません。各メソッドは 1 回の短いストレージトランザクションで構成され、Worker は 2 つのメソッド呼び出しの合間で外部 API を呼び出し、観測した結果を `LiveState` へ報告します。`LiveState` 自身の処理から外部処理を開始する必要がある場合は、`ctx.exports` を介して Worker の `LiveEffects` エントリーポイントを呼び出します。`LiveEffects` のメソッドは実際の処理を `waitUntil` に積んで即座に返却するため、Worker が外部サービスの応答を待っている間も `LiveState` 側は数ミリ秒で完了します。

スケジュール実行されるタスクは次の 2 つだけです。

- OBS の再接続猶予期間が経過した配信の終了処理（「インジェストのライフサイクル」を参照）
- 終了した配信の開始通知の削除処理（「通知」を参照）

どちらも `LiveState` のアラームによって駆動します。アラームは状態を変更する同一トランザクション内で設定するため、対応するアラームなしに期限データだけが保存されることはありません。アラームがセットされるのは OBS の再接続を待っている配信か、削除待ちの通知が存在する間だけであり、それ以外のときは何も動作しません。なお、アラームはあくまで起動のトリガーにすぎず、本当の期限は `lives.grace_expires_at` が保持しています。`LiveState` のすべてのメソッドは処理の冒頭で期限切れの配信を終了させるため、アラームの発火が遅れても後続リクエストが期限切れの配信を参照することはありません。

トランザクションには `ctx.storage.transaction()` を使用しています。この選択は実行時挙動の観察結果に頼るのではなく、Durable Objects ストレージの公式ドキュメントに明記された仕様に基づいています。SQLite ストレージでは、クロージャの実行中に `ctx.storage` に対して行われたすべてのストレージ操作がそのトランザクションの一部となり、アラーム操作も他のストレージ操作と同じ規則に従います。処理が失敗した場合は、ドキュメントで規定された手順に従い `rollback()` を呼び出して変更内容を破棄します。一方 `transactionSync()` は同期処理しか対象にできないため、Promise を返すアラーム操作をその中で呼んでもトランザクションに含まれません。したがって `transactionSync()` は、SQL のみを実行するコンストラクタ内のスキーママイグレーションに限定して使用しています。

## ロギング

Cloudflare Workers の呼び出しログ（Workers Logs）がメソッド・URL・ステータス・所要時間といったリクエスト単位のメタデータをすでに記録しているため、アプリケーションロガーではアクセスログを重複出力せず、構造化イベントログのみを出力します。認証済みの `/api/*`、`/play/*`、`/ingest/*` リクエストでは利用可能なユーザー／セッション識別子とともに 1 件の `info` イベントを出力し、リクエストの相関追跡は Workers Logs に委ねます。

`LOG_LEVEL` でアプリケーションログの詳細度（`debug`、`info`、`warn`、`error`、`silent`）を制御します。本番環境で未設定の場合のデフォルトは `info` です。警告やエラーには正規化されたエラーメタデータを含めますが、生の Bearer トークン、JWT、認可コード、Cookie、シークレットは絶対に出力してはなりません。

## ストレージスキーマ

テーブルは `LiveState` の SQLite ストレージ上に置かれ、その構造は `worker/database.ts` の `SCHEMA_MIGRATIONS` のみによって定義されます。各エントリが 1 つのスキーマバージョンを表します。`LiveState` は起動時に、どの RPC 呼び出しも処理する前に `schema_migrations` に未記録のバージョンを順次適用するため、Worker のデプロイ自体がそのままストレージのマイグレーションになります。スキーマを変更する際は必ず新しいエントリを末尾に追加し、デプロイ済みのエントリは絶対に編集しないでください（すでに適用済みのインスタンスでは再実行されないためです）。

Worker の Vitest スイートは `@cloudflare/vitest-plugin` によって `workerd` 上で実行され、本番と同じ SQLite ストレージを持つ実際の `LiveState` に対して同じ SQL 文・トランザクション・アラームを動かします。そのため、スキーマやクエリの誤りはデプロイ後ではなく `pnpm test` の時点で検出できます。ただし、各テストは空のストレージから始まるため、既存行のデータ移行や変換を伴うマイグレーションが既存データを正しく処理できるかまではテストで保証できません。

## D1からの切り替え

以前のバージョンでは配信状態を D1 データベース（`broad-db`）に保存し、Workflow（`whip-worker-live-end`）が配信終了処理を担っていました。`LiveState` はその両方を置き換えるもので、空の状態で開始します。D1 の行は意図的にインポートしていません。切り替え前にデータの内容を確認したところ、すべてのテーブルが通常利用の中で自然に再構築されるため、破棄しても問題ないと判断したためです。切り替えを伴うデプロイには以下の影響があります。

- `live_tokens`: すべての配信者トークンが無効になります。配信者がサイト上で新しいトークンを発行して OBS に設定するまで、OBS からの `/ingest/:userId` リクエストは `401` になります。
- `users`: 次回ログイン時にユーザー情報が再保存されます。切り替え前からログイン状態のままのユーザーもトークン作成や配信は可能ですが、再度ログインするまでその配信は `/api/lives` に表示されません。認証 Cookie の有効期限は 1 日であるため、この状態は自然に解消されます。
- `lives`: デプロイ時点で配信中だった配信の情報は失われます。`/api/lives` から消え、視聴者には `404` が返り、メッセージ ID も行と一緒に消えるため開始通知は Discord 上に残ります。誰も配信していないタイミングでデプロイしてください。配信中にデプロイすると、配信者は配信を再開する必要があり、残った古い通知も手動で削除しなければならなくなります。

このデプロイによって古いリソースが自動削除されることはなく、切り替え後にそれらを参照する処理もありません。猶予期間中にスリープしていた Workflow インスタンスがあっても、実行すべきクラスが存在しないためそのまま停止します。切り替えが完了して問題ないことを確認したら、`wrangler workflows delete whip-worker-live-end` および `wrangler d1 delete broad-db` で両リソースを削除してください。

## 認証とトークン

Discord OAuth は長寿命のアプリセッションそのものとして使うのではなく、サーバーへの参加資格を検証する手段としてのみ使用します。Worker は Discord のアクセストークンを使って指定されたサーバー（ギルド）への所属だけを確認し、確認後直ちにそのトークンを失効（revoke）させたうえで、独自の `authtoken` JWT Cookie を発行します。

認可リクエストでは `guilds.members.read` スコープのみを要求します。所属確認で呼び出す `GET /users/@me/guilds/{guild.id}/member` のレスポンスにはアプリセッションで使うユーザー ID、ユーザー名、グローバル名、ニックネームがすべて含まれているため、`identify`（`/users/@me`）は要求しません。

フロントエンドでは、専用の認証チェック API が完了するまで初期描画をブロックしません。API モジュールが起動時に「現在のユーザー」「配信一覧」「ライブトークン状態」の 1 回限りの SWR プリロードを開始し、アプリのブートストラップコンポーネントが同じ 3 つの SWR キーを購読します。いずれかが `401` レスポンスを返した場合はそのキー上に `UnauthorizedError` 結果が保存されてログイン画面へ遷移し、`401` がない状態でいずれかのデータが正常に取得できれば初期ローディング画面からアプリ画面へ遷移します。個別のデータパネルも同じキーを参照しつつ独自のローディング／エラー状態を保持するため、重複リクエストを発行することなく全プリロードの完了を待たずに通常のアプリシェルを表示できます。

配信用クレデンシャルと視聴者認証は分離しています。OBS は Bearer ライブトークンを使用し、視聴者は JWT Cookie を使用します。ライブトークンは発行時にのみ画面に表示し、生トークンではなく `LIVE_TOKEN_PEPPER` を使った HMAC ハッシュを配信状態に保存します。

## 配信行（lives）のセマンティクス

`lives` テーブルの各行は配信者 1 人につき 1 件の配信を表します。`broadcast_id` は配信全体を通じて同じ値が保たれ、一方 `session_id` や保存されている `trackName` / `mid` は現在の SFU インジェストセッションに紐づく値です。これらは OBS の再接続をまたいで引き継げないため、再接続時は古い値を再利用せずその場で新しいセッション情報に置き換えます。`grace_expires_at` はインジェストセッションが通常稼働している間は `NULL` であり、猶予期間に入ると再接続期限（Unix エポックミリ秒）を保持します。

`LiveState` の各メソッドは単独かつ 1 つのトランザクション内で実行されるため、Durable Object 内部で状態遷移が交錯することはありません。ただし、Worker から Calls への問い合わせは `LiveState` への 2 回のメソッド呼び出しの間に行われます（行を読み取り、Calls にセッション状態を問い合わせ、その結果に応じて `LiveState` へ操作を依頼する）。そのため状態更新の SQL は、Worker が観測した `session_id` および `grace_expires_at` に対する Compare-And-Set になっており、遅延したリクエストがすでに再開または猶予期間入りした配信を誤って終了させることはありません。再開時に `session_id` が更新されるため、古いセッションを対象とした終了処理は無効（no-op）になります。

Worker は配信一覧を SFU と完全に同期させようとはしません。完全同期にはすべてのアクティブセッションをポーリングする必要があり、`/api/lives` としては高コストすぎるうえステートレスな Worker モデルに合わないためです。代わりにインジェスト開始や再生開始など、特定のユーザー／セッションがすでに指定されている操作の際にピンポイントで SFU の確認を行います。

## インジェストのライフサイクル

`POST /ingest/:userId` が正規の配信開始パスです。

- 配信者の配信が猶予期間内であれば、新しい SFU セッションでその配信を再開します。行のセッションとトラック情報が置き換えられ、新しい開始通知は送信されません。
- 保存されているセッションが SFU 上で非アクティブになっており（OBS が `DELETE` を送らずにクラッシュまたは回線断を起こしたケース）、かつ過去 60 秒以内にいずれかのリクエストでアクティブ状態が確認されていた場合は、OBS の再接続とみなして同様に新しいセッションで配信を再開します。
- 保存されているセッションが非アクティブで、直近のアクティブ確認もない場合は、その配信を終了させて行を削除し（通知も削除キューへ登録）、新しい配信として開始します。
- 猶予期間がすでに経過していた場合は、インジェスト処理が参照する前に `LiveState` が期限切れの配信を終了させているため、新しい配信として開始します。
- 保存されているセッションがまだアクティブな場合は、2 本目のインジェストを拒否します。確認対象とするのは、そのユーザーの保存済み SFU セッションのみです。
- このインジェストのネゴシエーション中に同一配信者の並行インジェストが先行して行を作成または再開していた場合は、主キー制約エラーで失敗させる代わりに同じように後発のインジェストを拒否します。開始通知を行うのは行の確保に成功したインジェストだけであり、拒否された側の Calls セッションは Calls 側の自動クリーンアップに委ねます。

`DELETE /ingest/:userId/:sessionId` だけでは意図的な停止と再接続を区別できません。不安定な WHIP 接続で頻発するものも含め、OBS は再接続のたびに毎回 `DELETE` を送信するためです。ここで配信行を削除してしまうと再接続のたびに Discord 通知が削除・再投稿されてしまいます。

そのため `DELETE` を受けた際は即座に終了させず、60 秒間の猶予期間を開始します。インジェストのトラックを閉じつつも配信行と開始通知は残し、`LiveState` のアラームを期限時刻に設定します。期限までに新しいインジェストが配信を再開しなければ、`LiveState` が行を削除して Worker に通知を削除させます（「通知」を参照）。この設計のトレードオフとして、意図的に配信を停止した場合でも通知の削除が約 1 分遅れます。同一セッションに対する重複した `DELETE` は、新たな猶予期間を上書き開始せずに受け入れます。

OBS はアプリを閉じたときでも `DELETE` を送信するため、`DELETE` が送られないのはクラッシュやネットワーク切断のときに限られます。こうした異常終了をポーリングで常時監視することはしません（`LiveState` は SFU を呼び出してはならず、配信中ずっとポーリングし続けるとまれなケースのためにリクエストを浪費するためです）。異常終了は、その配信者に対する次のインジェストまたは再生リクエストで保存済みセッションが非アクティブと判明したときに検出されます。なお、Calls はクライアント接続を失ってから約 30 秒後にセッションをガベージコレクション（GC）し、その後 API に対して非アクティブを返すようになります。

`DELETE` が送られない場合、Worker はセッションがいつ失われたかを知ることができないため、直後の OBS 再接続と、何日も後に行われた新規配信目的のインジェストとをそのままでは区別できません。それでも再通知なしで再接続を再開できるようにするため、保存済みセッションがアクティブであることを確認したリクエストはその時刻を `session_seen_active_at` に記録します。記録するのは「まだセッションがアクティブなため拒否されたインジェスト」（Calls が GC を完了するまで再接続中の OBS がリトライを繰り返すため）と「再生リクエスト」（メディア停止後も視聴者が送り続けるため）です。最後のアクティブ確認から 60 秒以内に非アクティブが検出されたセッションは、つい先ほど失われたものと判断します。この 60 秒というウィンドウは `DELETE` 後の猶予期間と同じ長さであり、OBS の伸びていく再接続間隔と、後述する生存時刻の書き込み間隔の両方を吸収できるようにしています。

- インジェストの場合は、通知せずに配信を再開します。
- 再生リクエストの場合は、遅れて届いた `DELETE` と同様に扱って 30 秒間の猶予期間を開始し、`503` を返します。Calls がセッションを GC するまでのおよそ 30 秒と合わせると、`DELETE` を受けた場合（60 秒）とほぼ同じ時間だけ配信の復帰を待つことになります。最初の生存確認から Calls への問い合わせまでのわずかな合間にセッションが切れた再生処理も、直前にアクティブを確認しているため同じ扱いになります。

例えば、ネットワーク切断から 30 秒以上経ってから OBS が復帰し、かつ誰も視聴していなかった場合のように、GC 直前に誰もセッションのアクティブを確認していなかったときは、次のインジェストで新しい通知を伴う新規配信を開始します。これは、はるか後に開始された別配信が通知なしで暗黙に再開されてしまうのを防ぐため許容している仕様です。

`session_seen_active_at` への書き込みはセッションあたり最大でも 10 秒に 1 回に抑えています。Worker は読み取ったばかりの行をすでに持っているため、前回の記録が十分新しければ `LiveState` への更新呼び出し自体をスキップします。これにより健全な配信に参加する視聴者が `LiveState` を呼び出す回数は 2 回ではなく 1 回で済みます。並行するリクエスト向けに `UPDATE` 文側でも間隔チェックを繰り返しています。この記録はベストエフォートであり、記録がなければセッション喪失時は従来通り即座に配信終了となります。

## 再生のライフサイクル

`POST /play/:userId` は視聴者の JWT Cookie で認証され、再生セッションを作成する前に指定された配信のインジェストセッションが生きているかを SFU に確認します。これにより `/api/lives` を軽量に保ち、古いセッションの検出を実際にセッションを必要とする操作へ寄せています。

配信が猶予期間にある間、`POST /play/:userId` は SFU を呼び出さずに `Retry-After` ヘッダー付きの `503` を返します（保存されていたトラックは `DELETE` によってすでに閉じられているためです）。したがってクライアントにとって `404` は配信が完全に終了したことを意味します。再生リクエストが保存済みセッションの非アクティブを検出したものの、処理の合間に配信行が変化した（OBS が `DELETE` を送ったか再開した）ために行を終了できなかった場合も、視聴者が新しい状態に対してリトライできるよう `503` を返します。つい先ほど失われたばかりのセッションについても、「インジェストのライフサイクル」で説明した通り即座に終了させず短い猶予期間を開始します。`/api/lives` は猶予期間中の配信も一覧に含め続けますが、期限を過ぎた配信はアラームの発火が遅れていても決して一覧に載りません（`LiveState` がどの呼び出しに応答する前にも期限切れ配信を終了させるためです）。

再生の `DELETE` リクエストは、Worker が返した WHEP セッション URL に埋め込まれたトラック `mid` のみを閉じます。フロントエンドは保存データからセッション URL を再構築せず、返却された `Location` をそのまま使わなければなりません。再生セッションを作成した視聴者だけがそのセッション ID を知るため、セッション ID を視聴者ごとに紐付けて管理することはしていません。

再生の `DELETE` はベストエフォートです。`POST /play/:userId` の処理中に視聴者が切断した場合、Worker がすでに Calls の再生セッションを作成していたとしてもクライアントはリクエストを中断するため `DELETE` は送りません。誰もそのセッションに接続しないためメディアは流れず、やがて Calls によってクリーンアップされます。

## WHEPクライアントの設計判断

フロントエンドの WHEP クライアントは汎用的な WHEP クライアントではなく、Cookie/JWT で視聴アクセスを保護する本 Worker の `/play/:userId` エンドポイント専用として設計しています。

クライアントは SDP オファーを `POST` する前にローカルの ICE 収集完了を待ちます。現在の SFU 経路が実質的にノン・トリクル（non-trickle）であるため、初期接続のレイテンシを少し犠牲にしてでも接続の確実性を優先しています。WHEP 仕様においてトリクル ICE は任意であり、Worker の `PATCH` ルートは `application/trickle-ice-sdpfrag` 用ではなく `406` カウンターオファーへのアンサー送信専用に予約されています。

TURN 認証情報はオファー作成前に `/api/turn-credentials` から取得します。これは汎用的な WHEP の `OPTIONS`/`Link` 探索ではなく、アプリ固有の認証済みエンドポイントです。

TURN レスポンスではポート 53 の ICE URL を除外しています。Cloudflare はプライマリポートと代替ポートの両方を返しますが、ブラウザが代替ポート 53 をブロックすることが Realtime SFU のドキュメントにも記載されています。トリクル ICE なら候補を 1 つ無駄にするだけで済みますが、このアプリは `POST`/`PATCH` の前に完全な ICE 収集完了を待つため、ポート 53 を除外することでブラウザ側のタイムアウト待ちを回避できます。

カスタムレスポンスヘッダー `Wish-Live-Track-Count` により、フロントエンドへ期待される保存済み配信トラック数を通知します。インジェストが保存した数より少ないトラックしかネゴシエーションできなかった場合、クライアントは劣化した接続を正常とみなさず、不完全なセッションとして再接続を行います。

## フロントエンドのリカバリー

再生のリカバリーは視聴者（クライアント）主導で行い、無限にリトライし続けないよう上限を設けています。フロントエンドは特定のセッションで期待されるトラックの欠落、ストール（停止）、切断が起きたときに再接続します。クライアントは待機を続けるかどうかの判断基準（source of truth）として再生エンドポイントのステータスを参照します。`503` は利用可能なセッションがないものの配信自体は存続していることを意味するため、初回ロード時であっても固定の 2 秒間隔（Worker が返す `Retry-After`）でリトライし続けます。`404` は配信終了を意味するため即座に再生を終了します。サーバー側の状態を正としてポーリングするため、リトライには指数バックオフではなく固定間隔を使います。

配信終了を処理するアラームが遅れたとしても、猶予期間経過後の応答では Worker が `404` を返すため、通常クライアントはサーバー応答から配信終了を知ります。それでも、障害時や `503` 応答を返し続けるサーバーを永遠にポーリングし続けないよう、安全網として固定の時間枠（75 秒）でタイムアウトします。視聴者がストールを検知するのは通常 OBS が `DELETE` を送った数秒後になるため、この時間枠は Worker の 60 秒間の配信者再接続猶予期間より長く取る必要があります。`503` 以外の 5xx レスポンスやネットワークエラーは初回試行時には失敗として扱い、壊れたサーバーが初回ロード時にきちんとエラーとして表面化するようにしています。これらがリトライされるのは、確立済みセッションが切断された後や `503` 応答の待機中など、すでに再接続フェーズに入っている場合のみです。サーバーが `503` を返し続けたまま時間枠が切れた場合、Worker が配信終了を確定させていないため、再生は「終了（ended）」ではなくエラーとして終了します。

ストール検知では、一般的な配信終了パスを検出する必須手段としてレシーバーごとの受信バイト数（`bytesReceived`）を監視します。配信者が配信を終えた際、視聴者側では「SFU セッションの存在、ICE 接続状態、ネゴシエーション済みトラック数はいずれも正常に見えるのに RTP パケットだけが届かなくなる」という状態がよく発生します。期待される各トラックでメディアが流れ続けているかをブラウザ側で証明できるのは `bytesReceived` だけであるため、これが停止した配信を再接続／終了処理へ導く主要な経路となっています。バックグラウンドタブでのタイマー間引き（スロットリング）による誤検知を避けるため、この監視はドキュメントが可視状態（`visible`）の間だけ動作します。また本アプリは高画質視聴に適した安定回線を前提としているため、短いストールで再接続を行います。

トラック検出にも別のタイムアウトを設けています。`bytesReceived` の監視は、期待されるすべてのインバウンド RTP レシーバーがブラウザの統計情報に現れてからでないと機能しないためです。Worker が保存済みトラック数を 2 と通知したにもかかわらず PeerConnection にレシーバーが 1 つしか現れない場合、たとえ ICE が接続済みであっても再生セッションは不完全であるため、クライアントは部分的な再生を受け入れずセッションを作り直します。

## 通知

開始通知は `POST /ingest/:userId` が新しい配信を開始したときに送信されます（インジェスト URL に `notify=false` または `notify=0` が指定されている場合を除く）。配信の再開時には一切送信されません。

Discord への配信開始通知はベストエフォートです。配信終了時にメッセージを削除できるよう、Worker は Discord に対し作成されたメッセージ ID を返すよう要求します。この ID はインジェストセッションごとではなく `broadcast_id` に紐づけて保存されるため、通知送信中に再接続が起きても孤立しません。メッセージ ID は JavaScript の `number` に収まらない 64 ビットの Snowflake であるため、10 進数文字列として保存し、Worker と `LiveState` の間でも 10 進数文字列として受け渡します。

通知の削除は `LiveState` 自身が起点となって開始する唯一の外部連携ですが、`LiveState` 自身はその通信を実行できません（「ランタイムモデル」を参照）。そのため配信を終了する際、行を削除するのと同一トランザクション内でメッセージ ID を `notification_deletes` アウトボックスへ移します。アラームが発火すると期限を迎えたエントリにリースを設定し、まとめて Worker の `LiveEffects.deleteStartNotifications` へ引き渡します。同メソッドは即座に制御を返して `waitUntil` 内でメッセージ削除を実行し、完了した削除の ID を `settleNotificationDeletes` で `LiveState` へ報告します。報告を受けた `LiveState` は該当エントリをアウトボックスから削除します。ここでいう「完了」とは、Discord がメッセージを削除したか、メッセージがすでに削除済みであるなど再試行しても成功し得ない状態を指します。

ネットワークエラー、タイムアウト、`429`、5xx で失敗した削除は完了報告されないため、リース期限が切れるとアラームが再度払い出します。リース期間は Worker の `waitUntil` が実行され得る 30 秒をカバーする 30 秒から始まり、試行のたびに倍増するため、計 6 回の試行がおおよそ 15 分間に収まります。最後の試行でも 30 秒以内に削除を完了できなければ、そのエントリは `live_notification.delete_abandoned` 警告を出力して破棄し、メッセージは Discord 上に残ります。このアウトボックスは少なくとも 1 回（at-least-once）実行されるため同じメッセージが 2 回削除されることもあり得ますが、2 回目の削除に対して Discord は `404` を返し、それによって完了扱いとなります。

リクエストがセッションの非アクティブを検出して終了させた配信でも、同じように削除をキューへ登録します。実行期限は現在時刻（即時）とするため、同じメソッド呼び出し内で設定されたアラームが直ちに削除処理を払い出します。配信終了後に通知 ID が到着した場合、`LiveState` は保存せず代わりに削除キューへ登録します。ID を保存する呼び出しが一時的な Durable Object エラーで失敗した場合、Worker は新しいスタブを取得して 1 回だけリトライします（このメソッドは同じ ID で繰り返し呼び出しても安全です）。それでも保存に失敗した場合、Worker は ID が保存されたかどうかを判別できないため、Worker 自身がそのメッセージを削除します。

通知の送信・削除の失敗はログに記録されますが、インジェストや再生のクリーンアップ処理を妨げることはありません。

## 先送りしている機能

クライアントへの配信状態のプッシュ配信は意図的に見送っており、引き続きクライアント側および通常の HTTP リクエストを状態同期のトリガーとしています。この用途で SSE（Server-Sent Events）を追加しないでください。SSE 接続を保持している間は Durable Object がハイバネートできなくなるため、誰かがページを開いている間ずっと `LiveState` に課金が発生してしまいます。もし将来的に配信状態のプッシュ配信が必要になった場合は、ハイバネート可能な WebSocket（Hibernatable WebSockets）での実装を検討してください。
